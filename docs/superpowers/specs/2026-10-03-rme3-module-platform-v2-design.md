# RME3 Module Platform v2 — design, AI authoring, Connections, safe evolution, official catalog

## 1. Feature title

RME3 Module Platform v2: module quality and AI authoring, UI building blocks, Connections between
custom and core modules, safe schema evolution, Builder onboarding, and the official module catalog.

## 2. Status

Approved (2026-10-03, owner decisions recorded in section 3.4).

## 3. Context

### 3.1 How modules work today

- Official modules (inventory, contacts, hr, projects, ...) are compiled into the app: manifests in
  `apps/api/src/manifests/official/`, routes/services in `apps/api/src/routes/**`, screens in
  `apps/desktop/src/modules/**`. Every instance ships all of them.
- RME3 custom modules (`custom.*`, `community.*`) are installed at runtime from the Module Builder or a
  ZIP: tables from `defineModel` (Runly ORM, `module-schema-migration-service.js` +
  `packages/module-engine/src/schema-diff.js`), API mounted by `route-loader-service.js`, React
  components bundled with esbuild by `module-bundler-service.js` and loaded by
  `apps/desktop/src/shell/ModuleBundleLoader.jsx`.
- Custom modules receive `{ prisma, requirePermission, cache, moduleContext }` where `moduleContext`
  carries `notifications`, `files`, `relations` (read/search of 9 system entity types through
  `relation-targets-service.js`), `ai` and `cleanup`.

### 3.2 What owners and pilot users hit

Pilot users built modules with this flow: create a module in the Builder, add one entity and one field
(mandatory), switch to developer mode, download the ZIP, ask ChatGPT/Claude to implement the spec,
upload the ZIP. Results:

1. Screens look flat: inputs one per line, no icons, not responsive.
2. External AIs misuse `@runly/ui` (invented props, native `<select>`/`<input>`), skip icons.
3. Many upload/compile errors before anything works.
4. Updating a module whose fields changed fails (blocked migrations).
5. Custom modules cannot add data to core screens (e.g. extra fields on an inventory item that are
   visible, editable and searchable from Inventory).

### 3.3 Root causes found in the code (2026-10-03)

1. **Tailwind classes used by module bundles do not exist.** Module components are compiled with
   esbuild only; the CSS is generated by the desktop build from `apps/desktop/src` and
   `packages/ui/src`. Probing the built CSS: `md:grid-cols-3`, `gap-7` exist; `p-7`, `lg:col-span-3`,
   `md:grid-cols-6`, `size-14`, `ring-emerald-500`, `lg:grid-cols-[2fr_1fr]` do not. Any class not
   already used by the app silently does nothing.
2. **The AI gets no component contract.** `packages/module-compiler/src/runtime-catalog.json` lists
   `@runly/ui` as `"PageHeader, Card, Button, ... "`; no props, no examples, no icon list.
3. **The scaffold example is a placeholder** (`templates/custom.js`: a "Probar toast" button and two
   cards). AIs imitate examples far more than they follow written rules.
4. **No high-level building blocks.** Every screen is assembled from primitives, by hand.
5. **Schema diff only allows additive changes** (`schema-diff.js`): rename = drop + add (blocked),
   type change `UNSUPPORTED`, new required column on a populated table `UNSUPPORTED`, drop
   `DESTRUCTIVE`, new unique index `UNSUPPORTED`.
6. **No cross-module write contract.** Custom modules get raw `prisma`; writing core tables bypasses
   permissions, audit and business rules. `exposes`/`consumes` are declarative only;
   `packages/core/src/events.js` is an in-memory bus not used by the API.
7. **Core modules hard-delete** in places (`contacts-service.js` `delete`/`bulkDelete` use
   `prisma.contact.delete`/`deleteMany`); others soft-delete (`inventory-service.js` `deleteItem` sets
   `enabled=false`). Anything attached to core records must survive both.

### 3.4 Owner decisions

- D1. Program order: 1 quality/AI authoring, 2 UI kit, 3 Connections, 4 safe schema evolution,
  5 Builder onboarding, 6 official catalog + services API.
- D2. Connections: a central registry plus a central index table, kept in sync by the database
  (triggers), not by application code.
- D3. Core form saves are **atomic** with their connection data (option A): a single "Guardar" either
  persists the core record and every connection section, or nothing.
- D4. A custom module chooses exactly which of its fields are offered per connection and per surface;
  the company admin can only narrow that selection.
- D5. Deletion must work in every path: soft delete, hard delete (single and bulk), module disable,
  uninstall, reset, hard purge, company removal.
- D6. Catalog modules are free for now; licensing is a future enhancement (section 28).
- D7. Name in UI: **"Conexiones"** (sidebar entry in each core module, manifest key `connections`).

## 4. Problem

Building a good-looking, working RME3 module is hard for both visual Builder users and external AIs;
modules cannot evolve their schema after release; custom modules cannot extend core modules' screens,
search and saves; and there is no safe way to distribute and update official extension modules.

## 5. Goals

1. Any Tailwind utility written in a module component renders, with the Runly theme, light and dark.
2. A ZIP gives an external AI a complete, accurate contract: component props + examples, icon names,
   golden reference screens generated for the module's own entities, and a local check tool.
3. Upload reports flag design violations (native controls, window dialogs, missing `PageHeader`,
   hardcoded colors, emojis) with file and line.
4. `@runly/ui` offers high-level blocks so a good screen needs ~40 lines: `ModulePage`, `FormSection`,
   `FieldGrid`, `StatCard`, `FilterBar`, `DetailHeader`, `EntityForm` (schema-driven) and the
   `useEntity` data hook through a module runtime context.
5. Custom modules can connect to core entities (first: `inventory_item`) with two kinds: `fields`
   (1:1 extra fields) and `related` (1:N records), choosing fields per surface (form, detail, list
   column, search).
6. Core detail screens show connections inline with a one-line `ConnectionSlot`; any core screen that
   already publishes a record context (`useMiraiRecordContext`) but has no slot yet gets a shell-level
   "Conexiones" button that opens the same sections in a `Sheet`, with zero per-screen code. Core
   forms show and save connection sections atomically (D3); core list search finds records by
   connected fields.
7. Connection data stays consistent under every delete path (D5), enforced by foreign keys and
   triggers at the database level.
8. Module updates support rename, archive, safe type change, required fields with backfill, and
   module data migrations, transactionally, with a pre-update backup and a dry-run report.
9. Builder onboarding: start from templates, no mandatory first entity, "Crear con IA" (internal
   MirAI generating a module definition) and "Preparar para IA externa" (ZIP + ready prompt).
10. Official modules are listed from a signed catalog at runly.mx and installed/updated from the app;
    official modules use a typed cross-module services API with admin consent.

## 6. Non-goals

1. Licensing/payment of catalog modules (D6).
2. A visual page builder for arbitrary React layouts (the layout designer stays as is).
3. Connections between two custom modules in v1 (the renderer path makes it possible later).
4. Editing connection data inline in core list tables (list shows read-only columns).
5. Migrating existing core screens to a shared record-screen skeleton.
6. Moving existing default modules (POS, storefront, fleet...) out of the core into the catalog.
7. An MCP server for external AIs (future enhancement).
8. Physical `DROP COLUMN` in automatic updates (explicit purge only).
9. Replacing inventory's own per-company custom fields.

## 7. User stories

1. As a module author using ChatGPT/Claude, I want the ZIP to contain everything the AI needs so the
   first generated screens look like Runly and compile.
2. As a module author, I want the upload report to tell me exactly which lines break Runly design
   rules so the AI can fix them in one pass.
3. As a Builder user, I want to start from a template or describe my module to MirAI so I do not have
   to create a placeholder entity first.
4. As a module author, I want to declare that my "Calibraciones" module adds 2 fields to inventory
   items so they show and save inside Inventory.
5. As a company admin, I want a "Conexiones" screen in Inventory to see which modules connect, which
   fields they add, and switch them on/off per surface.
6. As an inventory user, I want to edit an item and its connected fields and press "Guardar" once.
7. As an inventory user, I want to search items by a connected field (e.g. certificate number).
8. As an admin, I want deleting a contact or uninstalling a module to never leave broken or orphaned
   connection data.
9. As a module author, I want to rename a field or make it required in v1.1 without breaking
   installations that already have data.
10. As an admin, I want to install and update official modules from the app and see what each one
    will be allowed to read and change before accepting.

## 10. Data model

All new tables are core tables managed by Prisma (they are platform infrastructure, not RME3 module
tables). IDs are UUID v7 (`@default(uuid(7)) @db.Uuid`).

### 10.1 `ModuleConnection` (`module_connection`) — registry and per-company config

| Column | Type | Notes |
|---|---|---|
| id | uuid | |
| company_id | uuid FK `company` ON DELETE CASCADE | |
| module_key | text | source custom module |
| connection_key | text | stable key from the manifest (`calibracion_item`) |
| kind | text | `fields` / `related` |
| target_type | text | `inventory_item`, `contact`, ... |
| source_entity | text | entity name in the source module |
| source_table | text | physical table of the source entity |
| status | text | `pending` / `active` / `disabled` |
| field_config | jsonb | `[{ field, form, detail, column, search, order }]` (admin narrowing of offered set) |
| sort_order | int | section order on the core screen |
| offered_version | text | manifest version that declared it |
| created_at / updated_at | timestamptz | |

Unique `(company_id, module_key, connection_key)`. Index `(company_id, target_type, status)`.

### 10.2 `ConnectionRecord` (`connection_record`) — central index (projection)

| Column | Type | Notes |
|---|---|---|
| id | uuid | |
| company_id | uuid | |
| module_key | text | |
| connection_key | text | |
| target_type | text | |
| target_id | uuid | the core record |
| source_record_id | uuid | row in the source table |
| enabled | boolean | mirrors source `enabled` |
| data | jsonb | raw values of **all offered fields** (filtered at read by `field_config`) |
| search_text | tsvector | built from offered fields flagged `search` in the manifest |
| updated_at | timestamptz | mirrors source `updated_at` (used for concurrency) |

Unique `(module_key, connection_key, source_record_id)`. Indexes:
`(company_id, target_type, target_id)`, GIN on `search_text`, `(module_key, connection_key)`.
No FK to the target (polymorphic); consistency comes from 10.3 and 10.4.

### 10.3 Source tables (custom module side)

- `fields` kind: the source entity table gets a `target_id uuid NOT NULL` column with
  `UNIQUE (company_id, target_id)` and a real FK `REFERENCES <target table>(id) ON DELETE CASCADE`.
- `related` kind: the existing external relation column (`targetExternal`) gets a real FK with the
  action derived from the relation's `onDisable`/`onTargetDelete` policy:
  `cascade` → `ON DELETE CASCADE`, `setNull` → `ON DELETE SET NULL`, `restrict` → `ON DELETE RESTRICT`.
- Runly ORM creates these FKs only when the table/column is created for a connection (additive);
  for an existing column, Phase 4's migration runner validates orphans first (dry-run count), then
  `ADD CONSTRAINT ... NOT VALID` + `VALIDATE CONSTRAINT`.

### 10.4 Triggers (generated per connection, owned by Runly ORM)

`AFTER INSERT OR UPDATE OR DELETE ON <source_table> FOR EACH ROW` → function
`runly_conn_<hash>()`:
- INSERT/UPDATE with non-null target: upsert `connection_record` (data = `jsonb_build_object` of
  offered columns, `search_text` = `to_tsvector('simple', ...)` of searchable columns, `enabled`,
  `updated_at`).
- UPDATE that sets target to NULL (setNull) or DELETE (including FK cascades): delete the index row.
Trigger + function names are deterministic: `runly_conn_<module_slug>_<connection_key>`.

### 10.5 Target registry

Extend `relation-targets-service.js` entries with `table`, `pkColumn` (`id`), `companyColumn`,
`connectable: true`, `recordContextTypes` (UI aliases, e.g. inventory publishes `'item'`) and
`softDeleteColumn` (`enabled` when the target soft-deletes).

### 10.6 Schema evolution (Phase 4)

- `.module-definition.json`: every field gets an immutable `fieldId` (UUID v7 string) generated by the
  Builder; `defineModel` field options accept `id`. Previous model schemas stored by
  `module-schema-migration-service.js` keep the id per column.
- `ModuleSchemaBackup` (`module_schema_backup`): id, module_key, version_from, version_to,
  created_at, tables jsonb (`[{ table, backupTable, rows }]`), expires_at. Backup tables live in
  schema `runly_backup` as `<table>__<yyyymmddhhmm>`; a worker job drops expired ones (14 days).
- `ModuleDataMigration` (`module_data_migration`): module_key, name, checksum, applied_at,
  version (tracks `migrations/NNN-name.js` runs).

### 10.7 Catalog (Phase 6)

- `ModuleCatalogCache` (`module_catalog_cache`): one row, `fetched_at`, `payload jsonb`, `etag`.
- `ModuleServiceGrant` (`module_service_grant`): company_id, module_key, service_key
  (`runly.inventory:items.adjustStock`), granted_by, granted_at.
- `DomainEventOutbox` (`domain_event_outbox`): id, company_id, event, payload jsonb, created_at,
  processed_at, attempts, last_error.

## 12. API contract

All endpoints: `authMiddleware`, company scope via `X-Runly-Company-Id`, JSON errors
`{ error, code? }`.

### 12.1 Phase 1
- `GET /modules/:key/bundle.css` → `text/css` with the utilities used by the module's
  `components/` sources (generated on first request, cached by source hash; `200` with an empty body
  when the module has no components, so the loader never logs a failed stylesheet).
- `GET /modules/:key/preview/:previewId/bundle.css` → same for upload previews (written next to the
  preview bundle at check time).
- Upload/publish reports (`POST /modules/upload/preview`, Builder publish preview) gain
  `designReview: [{ file, line, rule, severity, message }]`.

### 12.2 Phase 3 — Connections
| Method & path | Purpose | Permission |
|---|---|---|
| `GET /connections?targetType=inventory_item` | connections for a target type with config + offered fields | `<target module>.connections.manage` or target read (read-only subset) |
| `PATCH /connections/:id` | `{ status?, fieldConfig?, sortOrder? }` | `<target module>.connections.manage` |
| `POST /connections/:id/activate` | accept a pending connection (runs index backfill) | `<target module>.connections.manage` |
| `GET /connections/records?targetType=&targetId=&surface=detail\|form` | sections + values for one core record | target read permission; per-section source entity read permission |
| `POST /connections/records/batch` | `{ targetType, targetIds[], surface:'column' }` → values per id for list columns (max 200) | target read |
| `POST /connections/rebuild` | `{ moduleKey?, connectionKey? }` rebuild index from source tables | `core.modules.manage` |

Core save contract (inventory first): `PATCH /inventory/items/:id` and `POST /inventory/items`
accept an optional `connections: { [connectionId]: { values, expectedUpdatedAt|null } }`.
Errors: `422 { error, code:'connection_validation', fields:{ '<connectionId>.<field>': msg } }`,
`409 { code:'connection_conflict', connectionId }`, `409 { code:'connection_restrict',
connections:[{ label, count }] }` on delete when a `restrict` FK blocks it.

### 12.3 Phase 4
- `POST /modules/:key/update/preview` (existing preview extended) → `operations[]` with
  `{ type, table, column, safety, description, needs?: 'backfill'|'conversion', failingRows? }`.
- Apply accepts `{ decisions: { [operationId]: { backfill?: value, onConversionFailure?: 'null'|'abort' } } }`.
- `GET /modules/:key/backups`, `POST /modules/:key/backups/:id/restore` (`core.modules.manage`).
- `POST /modules/:key/fields/:fieldId/purge` (explicit drop of an archived field, `core.modules.manage`).

### 12.4 Phase 5
- `POST /builder/projects/from-template` `{ templateKey, name, key }`.
- `POST /builder/projects/ai-draft` `{ description }` → `{ definition, diagnostics }` (requires
  `GROQ_API_KEY`/local AI; 503 `ai_unavailable` otherwise).
- `GET /builder/projects/:id/ai-prompt` → `{ prompt }`.

### 12.5 Phase 6
- `GET /catalog` → cached catalog entries + install state.
- `POST /catalog/:key/install` `{ version, grants: string[] }`, `POST /catalog/:key/update`.
- Server-side fetch from `RUNLY_CATALOG_URL` (default `https://runly.mx/catalog/v1/index.json`),
  package download, SHA-256 + Ed25519 signature verification against the embedded public key, then
  the existing package install pipeline.

## 15. Module manifest impact

### 15.1 Custom module manifest — `connections`
```js
connections: [{
  key: 'calibracion_item',
  target: 'inventory_item',
  kind: 'fields',                 // 'fields' | 'related'
  entity: 'calibracion',
  label: 'Calibración',
  fields: [                       // offered set (D4); omitted fields are never shown in core
    { field: 'fecha_calibracion', form: true,  detail: true, column: true,  search: false },
    { field: 'certificado',       form: false, detail: true, column: false, search: true },
  ],
  onTargetDelete: 'cascade',      // related only: 'cascade' | 'setNull' | 'restrict'
  required: false,                // module can work without it
}]
```
`defineRunlyModule` validates it; the compiler emits it from Builder definitions.

### 15.2 Core module manifests
Connectable core modules declare `connectionPoints: { inventory_item: { surfaces: ['detail','form','column','search'] } }`
and the permission `<module>.connections.manage`, plus navigation item "Conexiones".

### 15.3 Official catalog modules
`official: true` is never trusted from the manifest; it is set by signature verification.
`consumes: { 'runly.inventory': ['items.read', 'items.adjustStock'] }`, `events: { subscribes: [...] }`.

## 18. RBAC/permissions

| Key | Guards |
|---|---|
| `inventory.connections.manage` (then `contacts.`, `hr.`, `projects.`) | Conexiones screen, `PATCH/activate` |
| target read (e.g. `inventory.item.read`) | `GET /connections/records*` |
| source entity read/update/create (`<slug>.<entity>.*`) | per-section visibility and save |
| `core.modules.manage` | rebuild, backups, restore, purge field, catalog install/update |

A user without the source entity permission does not see that section; on save, sections the user
cannot update are ignored server-side (their values are not sent by the UI either).

## 19. Multi-company behavior

`module_connection` is per company (activation and config). Index rows carry `company_id` copied from
the source row; every read filters by the active company. Triggers copy `company_id` from the source
row, never from session state. Catalog cache and installed packages are instance-wide; service grants
and connection activation are per company.

## 20. Files/storage impact

Connection fields of type `file` show through the source module's files capability (signed URLs);
no new storage prefixes. Module CSS is stored next to the bundle (`modules/custom/<key>/.runly/bundle.css`).
Catalog packages are cached under `modules/.catalog-cache/<key>/<version>.zip`.

## 21. Export/import requirements

Inventory CSV export gains optional connected columns (offered `column` fields). Archived-field purge
offers a CSV export of that column first. No import changes in v1.

## 23. Edge cases

1. Core record **soft-deleted** (`enabled=false`): connection rows are kept; detail/search exclude it
   because core queries already exclude disabled records; re-enabling restores everything.
2. Core record **hard-deleted** (contacts `delete`/`bulkDelete`): FK `ON DELETE CASCADE` removes
   `fields` rows and `cascade` related rows; `setNull` related rows get `target_id = NULL`; triggers
   remove their index rows in the same transaction. `restrict` makes the core delete fail; the core
   route maps the FK violation (`23503` on a `runly_conn_*` constraint) to `409 connection_restrict`.
3. **Bulk** hard delete with one restricted record: the whole statement fails (atomic); the message
   lists the blocking connection.
4. Source record **soft-deleted** in the custom module: trigger sets `enabled=false` in the index; the
   section shows empty for `fields` kind (a new save re-enables by upserting).
5. Source record **hard-deleted** (custom module purge/reset): trigger deletes index rows.
6. Source module **disabled**: index rows stay; reads filter out connections whose module is not
   `INSTALLED`+`enabled`; core forms do not send/save those sections.
7. Source module **uninstalled (preserve-data)**: `module_connection` rows → `disabled`; triggers and
   FKs stay with the preserved tables; reinstall reactivates and runs a rebuild.
8. Source module **reset**: tables truncated by the reset handler → triggers clear index rows
   (statement uses `DELETE`, not `TRUNCATE`, for connection tables; the reset path is updated
   accordingly) — verified by test.
9. Source module **hard purge**: `DROP TABLE ... CASCADE` drops triggers/FKs; purge also deletes
   `connection_record` and `module_connection` rows for the module in the same transaction.
10. **Company removed**: `module_connection` cascades by FK; `connection_record` rows are deleted by
    the company cleanup path (no FK, explicit delete) — added to the company deletion routine.
11. Core form save where the connection's module was disabled between load and save: section values
    are ignored with a warning toast, core record still saves (no partial data written for the
    disabled module).
12. Concurrency: `expectedUpdatedAt` differs from the source row → `409 connection_conflict`, nothing
    saved (atomic).
13. New core record (create) with connection values: target inserted first in the transaction, then
    connection rows with the new id.
14. Connection field removed or renamed by a module update: Phase 4 `fieldId` keeps renames working;
    removed offered fields disappear from `field_config` with an admin notice in Conexiones.
15. Admin narrows `search` on a field: reads filter by config; the index keeps all offered values
    (no rebuild).
16. Activating a connection on a company with existing source rows: activation runs a backfill
    (`INSERT ... SELECT` from the source table) in batches.
17. Type change with rows that fail conversion: preview reports the count and sample ids; the admin
    chooses "dejar vacío" (only for nullable) or cancel.
18. Update failure mid-way: the whole DDL+data migration runs in one Postgres transaction and rolls
    back; the backup is kept for 14 days for post-commit restores.
19. Tailwind class that collides with an app class: generated rules are identical; module CSS is
    utilities-only (no preflight/base) so it cannot restyle the shell.
20. Catalog unreachable/offline instance: catalog tab shows cached entries with "Sin conexión" state;
    installed modules keep working.
21. Signature mismatch: install refused with "El paquete no es auténtico".

## 24. Risks

1. **Trigger/FK SQL generated at runtime** could be unsafe → identifiers validated with the existing
   `safeIdentifier`, fixed templates, unit tests on generated SQL, and `assertSafeMigrationSql`.
2. **Atomic save couples core availability to custom module code** → validation runs before any
   write; disabled/errored modules are excluded at load time; write handlers are generated code with a
   fixed contract; a failing handler returns 422/500 with the section named, never a silent partial.
3. **FK on core tables blocks core deletes** (`restrict`) unexpectedly → only declared `related`
   connections with explicit `restrict` do it; default for `related` is `setNull`, for `fields`
   `cascade`; the Conexiones screen shows the policy.
4. **Tailwind compile at install** adds API dependencies and time → `@tailwindcss/node` +
   `@tailwindcss/oxide` in `apps/api`; compile only module sources; cache by bundle hash.
5. **Schema evolution bugs lose data** → mandatory backup before apply, transactional DDL, dry-run
   preview with real counts, tests per operation type.
6. **External AI still ignores rules** → golden examples + design review + typed contract shrink the
   gap; the kit makes the correct path the short path.
7. **Catalog code runs in-process with full DB access** → only Ed25519-signed packages are official;
   unsigned stay custom; public key pinned in the API build.
8. **File size limits** (`BlueprintCrudScreen.jsx` is already 1179 lines) → new code goes in new
   files; touched oversized files get split as part of the task that touches them.

## 25. Acceptance criteria

1. Given a module component using `p-7 lg:col-span-3 size-14`, when installed, then the rendered
   elements have those styles in light and dark themes.
2. Given a downloaded ZIP, then `docs/componentes.md` lists every exported `@runly/ui` component in the
   contract with props and an example, `docs/iconos.md` lists lucide names, and `docs/ejemplos/`
   contains list/detail/form/dashboard screens for the module's first entity.
3. Given a component with `<select>` and `window.confirm`, when uploaded, then the report shows two
   findings with file and line.
4. Given `EntityForm` with an entity schema of 8 fields, then it renders sections in a responsive
   two-column grid with an icon per field type, required markers and Zod errors.
5. Given "Calibraciones" with a `fields` connection to `inventory_item` offering 2 fields, when the
   admin activates it, then the inventory item detail shows a "Calibración" section with those 2
   fields and the item form shows them editable.
6. Given the item form with changed core and connection values, when "Guardar" succeeds, then both
   rows are updated in one transaction and the index row reflects the new values.
7. Given an invalid connection value, when saving, then nothing is persisted (core included) and the
   error is shown on that field.
8. Given an item search for a certificate number stored only in the connection, then the item appears
   in the inventory list results.
9. Given a contact hard-deleted with a `cascade` connection row and a `restrict` related row on
   another contact, then the first delete removes source and index rows, and the second returns 409
   with the blocking connection label.
10. Given the source module is uninstalled with preserve-data, then sections disappear from core
    screens and no core screen errors; after reinstall they reappear with the same data.
11. Given a hard purge of the source module, then no `connection_record`/`module_connection` rows
    remain for it.
12. Given a module update renaming a field (same `fieldId`), then the column is renamed and data kept.
13. Given an update adding a required field to a table with rows, then the preview asks for a
    backfill value and the apply fills it.
14. Given a failing conversion during apply, then no change is committed and the module still works
    on the previous version.
15. Given the new-module dialog, then a module can be created from a template without adding an
    entity manually.
16. Given the catalog tab with a tampered package, then install is refused.

## 26. Verification plan

Per phase: `node --test` on new unit tests (module-engine, module-compiler, api services),
`pnpm lint`, `pnpm build:web`, `node --check` on generated files, real API boot + curl smoke against
new endpoints (dev server owned by the user: reuse the running one, never start/kill it),
`node scripts/generate-module-developer-docs.mjs` (developer-docs test must pass), and manual
end-to-end in a running instance for the UI criteria (recorded as pending until done by the owner).
Connections deletion matrix (edge cases 1–10) is covered by an integration test that runs against a
disposable schema in the dev database inside a transaction that is rolled back.

## 27. Rollback plan

Every phase is additive and feature-flag free but reversible:
- Phase 1/2: revert commits; module CSS endpoint 404s harmlessly.
- Phase 3: deactivate connections (`status=disabled`) hides everything; dropping triggers/FKs via
  `POST /connections/rebuild { drop: true }` (internal) or reverting; Prisma migration has a manual
  down script in the plan (drop the two tables).
- Phase 4: backups + restore endpoint; reverting code leaves `fieldId` metadata unused.
- Phase 6: catalog tab hidden when `RUNLY_CATALOG_URL=off`; installed packages remain normal modules.
